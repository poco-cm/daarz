# DEC-2026-08-09-005 — Population and observability decisions

**Status:** recorded
**Order:** 2, phase 3
**Authority:** §8 Genesis matrix — implementation inside already-activated institutions
**Exit gate:** integration test with two agents, live census, wired logging, one real alert

---

## Decision 1 — The census holds no number of its own

`PopulationCensus` stores nothing. Every call to `take()` reads `agents/registry/` from
disk. A cached count is a statement about a moment that has passed, and a civilization
that misreports its own size cannot be bounded.

This is tested adversarially: `test_census_is_a_live_query_not_a_stored_number` mutates
the registry through a *separate* registry object, without calling any method on the
census, then asserts the census reports the new state.

## Decision 2 — A stopped agent is not an erased agent

`stop` changes status; it never deletes the record. The census therefore reports
`active`, `stopped`, and `total` separately. Deleting stopped agents would make the
archive of who ever existed unrecoverable, which §6 forbids in spirit.

## Decision 3 — Exactly two lifecycle states

`active` and `stopped`, with exactly two permitted transitions between them. No
`suspended`, `pending`, or `retired`, because nothing can currently enter or leave those
states. A redundant transition (activating an active agent) is refused rather than
silently accepted, so callers cannot mistake a no-op for a change.

## Decision 4 — Observability is wired at construction, not at run time

`AgentFactory` attaches the execution log and the alert handler when the agent is built.
An agent therefore cannot be constructed unobserved and then quietly run. Logging is a
property of existing, not an option chosen per run.

## Decision 5 — The alert fires from inside the breach

`BoundaryBreachAlert` is registered through `BoundaryEnforcer.on_violation`, which the
enforcer invokes *before* raising `BoundaryViolation`. The alert cannot be raised without
a breach, and a breach cannot pass silently. It is verified in both directions: one test
asserts a breach produces exactly one critical alert, another asserts a compliant run
produces zero.

## Decision 6 — One log file per agent, JSON Lines, append-only

Per-agent files avoid interleaving and let one agent's history be read without parsing
another's. `ExecutionLog.entries()` returns a named empty list rather than `return []`,
for the same procedural reason recorded in DEC-2026-08-09-004 decision 6.

## Evidence — actual output

Live demonstration of census, lifecycle, logging, and alerting together:

```
census before any agent : {'taken_at': 1786223650.793426, 'active': 0, 'stopped': 0, 'total': 0, 'active_ids': []}
census with two agents  : {'taken_at': 1786223650.7938914, 'active': 2, 'stopped': 0, 'total': 2, 'active_ids': ['agent-001', 'agent-002']}
agent-001 -> input_exhausted output 15 | cycles logged 5
agent-002 -> boundary | boundary 'max_operations' exceeded: limit=20, observed=21
alerts raised           : 1
alert                   : ALERT-0001 critical | Agent 'agent-002' exceeded its declared limit 'max_operations' (limit 20, observed 21). Execution was halted.
census after one stop   : {'taken_at': 1786223650.7950273, 'active': 1, 'stopped': 1, 'total': 2, 'active_ids': ['agent-002']}
```

Read directly from that output: the census moved 0 → 2 → 1 active in response to real
events; `agent-001` produced 15 from inputs 1..5 with all 5 cycles logged; `agent-002`
was halted by its own declared limit at operation 21 of a permitted 20; exactly one
critical alert was raised, naming the agent, the limit, and the observed value.
